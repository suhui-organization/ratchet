# 交付记录 0.6.0 —— 两种交付形态一条命令出

> 日期：2026-09-18。上一版见 [DELIVERY-0.5.0.md](DELIVERY-0.5.0.md)。

## 1. 这一版做了什么

`ratchet-report build` 现在能同时产出**两种交付形态**：

```console
$ ratchet-report build --dir delivery --policy policy.json --bundle share.json
  产物 2 份
    policy.json  1627 字节
    report.md    4266 字节
  分享包：share.json（8.0K）
```

| 形态 | 给谁 | 怎么用 |
|---|---|---|
| **目录** | 归档、邮件附件、内部留存 | `python3 verify.py <目录>` |
| **分享包**（单个 JSON） | 客户 / 外部审计 | 拖进验证页，哈希在**他的浏览器里**算 |

两种形态覆盖同一批文件，且内容哈希与清单一致——**不会出现"目录能验、分享包不能验"**。

## 2. 为什么保留两种形态

分享包是给"不想装任何东西"的收货方；目录是给要归档、要 diff、要进版本控制的人。
只留一种就会挡住另一类人。两种都由同一次 `build` 产出，它们之间不可能不同步。

## 3. 实测

```console
$ python3 -m pytest -q   →  22 passed

# 网页端算法复算：用与验证页完全相同的两个 API（crypto.subtle + TextEncoder）
$ node --input-type=module -e '…verify.ts 的同一份逻辑…' share.json
  2 份一致，0 份不一致
```

最后一条是关键：**分享包里的内容，用浏览器端那套算法算出来的哈希与清单完全吻合**。
这比"我觉得应该一致"强，因为它跑的是同一份算法。

## 5. 建议的下一步

到这里，"从采集到收货方独立验证"整条链路已经没有断点了。
下一步的分叉点不在工程上：

| 选择 | 什么时候选 |
|---|---|
| **拿它去做 3 次真实交付** | 如果目标是验证"有没有人愿意为此付钱"——这是唯一的证据来源 |
| L4 报告英文化 | 如果客户在海外 |
| L1 接 Claude Code | 如果目标客户的 agent 不是 Codex |

**我的建议是先做真实交付。** 工程侧的边际收益已经开始下降：
现在的形态已经够拿去见人了，而"有没有人愿意买"这条信息，任何一行代码都换不来。
