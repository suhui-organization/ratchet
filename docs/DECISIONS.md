# 决策记录

> 每条写清：选了什么 / 为什么 / 否掉了什么。有争议的决策必须留痕。

## D1 · 工程名 Ratchet

**选择**：`ratchet`（棘轮）。
**理由**：棘轮只能往一个方向转——正好是产品的核心不变量：**权限只能收紧，放宽必须显式**。
这个名字同时避免了与现有厂商（Warrant、Lasso、Zenith 等）撞名。

## D2 · Go 与 Python 的分工

**选择**：

| 语言 | 负责 | 理由 |
|---|---|---|
| **Go** | 机器上的引擎：工具清单解析、能力判定、策略编译、CLI | 编译成单个静态二进制。**目标机器不需要装 Node/Python** ——这是"装得上"的前提，也是上一代产品最大的分发教训 |
| **Python** | 交付物侧：合规映射、sha256 清单、独立验证器、后续的托管 API | 收货方（客户/审计）大概率有 Python 而没有 Go 工具链；验证器要能作为**单个文件**发出去 |

**否掉**：全部用 Go（验证器要编译，收货方门槛高）；全部用 Python（机器侧要求目标装 Python 与依赖）。

## D3 · 前端用 Nuxt（Vue）而不是 Next.js

**选择**：Nuxt 4 + Vue 3 + Tailwind。

**理由**：原始需求写的是 `vue + nextjs`，但 **Next.js 是 React 框架，与 Vue 不能共存**。
Nuxt 是 Vue 生态里与 Next 对等的元框架（同样是文件路由 + SSR + 构建产物），
因此按"Vue"这一侧落地。

**否掉**：React/Next（违背明确写在前面的 `vue`）。
**代价与退路**：如果实际想要的是 React，只需重做 `web/` 目录；
Go 引擎与 Python 交付物层完全不受影响——这是把前端独立成目录的原因之一。

## D4 · Web 端只做两页，不做控制台

**选择**：落地页 + 验证页（`/verify/:token`）。

**理由**：市场证据显示"云端控制台"是上一代产品烧掉大量时间却没有用户的地方（见
`deepseek-fin-harness/pod/docs/reposition/11-market-feature-analysis.md`）。
Web 端唯一不可替代的价值是：**让没有账号、不装任何东西的收货方，在自己的浏览器里
重算哈希并得出结论**。

**否掉**：dashboard、多租户、登录态、订阅计费。

## D5 · 未识别的工具默认 `approve`，不是 `deny`

**选择**：静态清单里名字无法判定能力的工具 → `approve`（挂起等人批），并标记
`needsReview`；`--strict-unknown` 时才降为 `deny`。

**理由**：`deny` 对"名字没命中词表"的工具过于激进——大部分 MCP 工具名不在词表里，
全判 deny 会让第一份策略直接不可用，用户就放弃了。`approve` 的效果同样是 fail-closed
（不能无人值守地执行），但保留了可用性；同时把所有待确认项列成一张清单。

**否掉**：默认 deny（不可用）；默认 allow（不安全）。

## D6 · 策略文件里内嵌判定依据

**选择**：策略 JSON 里带 `rationale`（每条判定为什么这么判）与 `needsReview`。

**理由**：这是产品对外的核心承诺——**每条判定都能追回依据**。
没有它，用户无法判断这份自动生成的策略是否可信，也就不会去维护它。

**否掉**：只输出干净的策略（好看，但不可审计）。
