# ASAS v0.1 — Agent Security Assurance Standard

**状态：Draft Specification（草案）。**

> 命名纪律：在出现**外部实现**之前，这份东西只能叫 specification，不能叫 standard。
> 一个只在自家仓库里自称"标准"的规范，会让最想争取的那批读者（审计员、CISO）立刻降低信任。
> 这条纪律本身就是筹码，见 §8。

---

## 1. 范围与非目标

**范围内**：agent 的**身份、权限边界、供应链完整性、运行时治理、可审计性、可验证凭据**。

**非目标（明确排除）**：模型对齐、提示词护栏、内容安全、模型能力评测。

**为什么排除**：模型层的控制是**概率性的、由模型厂商控制的**，且无法交给客户的审计员核验。
本规范只管一件事——**组织层的确定性要求，以及能被第三方独立验证的证据**。两者互补，不竞争。

## 2. 规范性术语

| 术语 | 定义 |
|---|---|
| **Agent** | 能自主调用工具/服务的软件实体，含现成产品与自研 |
| **Identity** | agent 使用的凭据主体。**共享凭据不构成合规 identity** |
| **Asset** | agent 可达的外部组件（MCP server / skill / plugin / tool） |
| **Delegation** | 权限由 A 授予 B 的行为，含作用域与到期 |
| **Attestation** | 由被评估方产出、**可被第三方离线独立验证**的机器可读凭据（格式见 `ASAS-A-v0.1.schema.json`） |
| **Unknown** | 无法枚举或无法判定的状态。**不得省略**——省略未知即审计欺诈 |
| **Silence** | 某段时间内"没有事件"。在本标准里，沉默必须可被证明，见 §6.6 |

## 3. 一致性模型

本标准有两种一致性主体，**不要混用**：

- **ASAS-Consistent Implementation**：工具/实现满足 §4 中标注为「实现」的要求。
- **ASAS-Attested Organization**：组织满足 §4 控制要求，并产出通过 §6 全部验证规则的有效凭据。

**四级（组织级）**

| 级别 | 名称 | 达成条件 |
|---|---|---|
| **L1** | 可见 | ASAS-1 全满足 + ASAS-3.5（未知显式） |
| **L2** | 边界 | L1 + ASAS-2（含委派收窄）+ ASAS-3 |
| **L3** | 可证明 | L2 + ASAS-5/6：能出凭据且**第三方离线验证通过** |
| **L4** | 持续 | L3 + ASAS-8：变更重证、门禁、遏制演练 |

## 3.5 追溯矩阵：每条要求必须能追到一个被实证的痛点

**本节是这份规范的合法性来源。** 一条控制要求如果追不到痛点，就是厂商在按自己的产品
划标准——评审人第一个会问的就是这个。因此规定：

> **任何 MUST 条款 MUST 能追溯到一条带实证的痛点；追不到的条款 MUST 删除或降级为 SHOULD，
> 并在表里写明理由。**

| 控制项 | 对应痛点 | 实证 |
|---|---|---|
| 1.1 具名责任人 | 看不见 agent 身份 | 92% 对 AI 身份无完整可见性（CSA，2026，n=235） |
| 1.2 Shadow AI 发现 | 未批准工具在跑 | 高管大幅低估 shadow AI 普遍度（Okta 2026）；58% 一年内出过事或擦边 |
| 1.3 未登记隔离 | 同上 + 无人负责 | 同上 |
| 1.4 NHI 生命周期 | 凭据共享/无人轮换 | Microsoft：agent 应为 first-class principal（不得共享凭据） |
| 2.1 默认 deny | 有身份不执行策略 | 86% 不为 AI 身份执行访问策略（CSA） |
| 2.2 判定带依据 | 判定不可复核 | 审计失败类目：可审计性不足（AvePoint 2026） |
| 2.3 任务/时限作用域 | 永久角色过宽 | NIST AI Agent Standards 短期缓解：作用域限任务与时限 |
| 2.4 委派只可收窄 | 子 agent 继承父权限 | NIST/CSA：子 agent 默认不得继承 orchestrator 权限集 |
| 2.5 委派过期 | 同上 | 同上 |
| **2.6 敏感资源二次批准** | **agent 已接进核心系统** | **71% 的 AI 系统可访问 ERP/CRM/财务，仅 16% 有效治理（CSA）** |
| 3.1 定版或书面豁免 | 供应链可被替换 | 未锁版本实测：16 个 server 中 12 个未锁（本项目实测） |
| 3.2 内容哈希 | rug pull / 产物替换 | CrowdStrike 三类攻击中的 rug pull |
| 3.3 描述哈希 | 工具投毒 / 影子工具 | CrowdStrike：tool poisoning / tool shadowing |
| 3.4 升级 diff | 同上 | 同上 |
| 3.5 未知显式 | 清单看起来干净但漏了 | 本项目实测：16 个 server 中 4 个根本枚举不出来 |
| 4.2 高危需批准 | 破坏性动作无刹车 | 实测 deny 面：kubectl_delete / uninstall_helm_chart / js_reset |
| 5.1 调用留痕 | 事后无法调查 | 审计失败类目：可审计性不足（AvePoint） |
| 5.2 不记参数值 | 审计与隐私冲突 | 企业不愿把业务数据交出去（采纳障碍，AvePoint 40%） |
| 5.3 防篡改 | 日志可被改 | 同上：可审计性不足 |
| **6.1–6.3 凭据与离线验证** | **要把答案交给第三方** | 采购/审计要求可核验证据（CSA 18% 有效治理 = 绝大多数拿不出证据） |
| 6.5 变更重证 | 一次性快照会过期 | 同上（供应链变更即失效） |
| 6.6 可验证的沉默 | 采集器本身可被做手脚 | 由 5.3 推出（若沉默不可证，5.3 无意义） |
| 7.1–7.2 合规映射 | 强制合规义务 | EU AI Act Art.11/15/17；ISO/IEC 42001 |
| 8.1 吊销时限 | 关不住被攻陷的 agent | 95% 怀疑既检测不到也关不住（CSA） |
| 8.3 谁碰过 X | 事后溯源第一个问题 | 同上 |
| 8.4 遏制演练 | 同上（能力未验证等于没有） | 同上 |

### 本表暴露的两处修正（已应用到上面的条款）

1. **2.6 从 SHOULD 升为 MUST**：它对应的是全套研究里最痛的数（71% 接进核心系统 / 16% 治理），
   之前按"实现难度"给了 SHOULD —— **那是按我们的能力划标准，不是按痛点划标准**。
2. **新增 4.4（MUST）**：必须把模型侧护栏与 agent 框架的安全信号**作为输入摄入**并能关联到具体调用。
   > **4.4 (MUST)** 若所治理的 agent 运行在带安全策略的模型/框架上，MUST 摄入其拦截与告警信号，
   > 并能在凭据里以 `signals[]` 呈现。理由：模型层控制是概率性且厂商持有的，组织层需要
   > 确定性的记录；两层互补，但不摄入就等于组织层面看不见。

### 明确追不到痛点、因此**没有**成为条款的东西

| 曾考虑 | 为什么不做 |
|---|---|
| "多租户/计费" | 与痛点无关，是厂商商业模式 |
| "跨客户威胁情报" | 缺收敛的威胁模型（NIST/CSA 仍在写），不足以支撑 MUST |
| "必须用容器部署" | 是手段不是要求；只保留一条相关 SHOULD（见 4.5） |

> **4.5 (SHOULD)** 采集 SHOULD 能在**不要求每位开发者手工操作**的前提下完成。
> 理由：采纳障碍本身就是痛点（AvePoint：40% 组织因采纳障碍延迟部署），
> "装在每个开发者的笔记本上"会让合规率长期停在低位。

## 4. 控制要求

措辞遵循 RFC 2119：**MUST = 强制**，**SHOULD = 建议**。

### ASAS-1 身份与资产
- **1.1 (MUST)** 范围内每个 agent 可枚举，含唯一 id、**具名人类责任人**、运行时。
- **1.2 (MUST)** 能发现未登记 agent（Shadow AI），并声明发现方式。
- **1.3 (MUST)** 未登记 agent 进入隔离态：不得访问受限资源。
- **1.4 (MUST)** 非人身份全生命周期可追溯（签发/轮换/吊销）；**共享凭据 MUST 被标记为违规**。

### ASAS-2 权限边界
- **2.1 (MUST)** 每个 agent 有显式策略，默认 `deny`。
- **2.2 (MUST)** 每条授权 **MUST 携带依据**（命中规则或关键词）；无依据的授权不合规。
- **2.3 (MUST)** 作用域 MUST 绑定任务与时限，不得是永久角色。
- **2.4 (MUST)** **委派只可收窄**：子集 ⊆ 父集，默认**不继承**。（对齐 NIST/CSA 对委派边界的短期缓解措施）
- **2.5 (MUST)** 委派 MUST 有过期时间；**未知委派链视为越权**。
- **2.6 (MUST)** 敏感资源（ERP/CRM/财务/密钥库）访问 MUST 有二次批准路径。
  （原为 SHOULD，2026-09-20 升为 MUST：它对应的是全套研究里最痛的数——71% 的 AI 系统
  可访问核心业务系统而仅 16% 有效治理。按实现难度把它降级，就是**按我们的能力划标准**。）

### ASAS-3 供应链完整性
- **3.1 (MUST)** 外部组件 MUST 定版；未定版 MUST 有**书面豁免与到期日**（开放式豁免不合规）。
- **3.2 (MUST)** 记录并校验内容哈希；变更 MUST 触发重证。
- **3.3 (MUST)** **工具描述与 schema 的哈希单独登记**——防投毒、影子工具、以及"产物没变但描述变了"。
- **3.4 (SHOULD)** 升级时给出"描述 / 能力 / 权限"三者 diff。
- **3.5 (MUST)** **未知 MUST 显式声明**（`unknown[]` 必须存在，可为空）。

### ASAS-4 运行时治理
- **4.1 (MUST)** 声明治理模式：`enforce`（存在执行点）或 `readonly`（只读）。**只读是合法答案，但必须声明**。
- **4.2 (MUST)** 高危动作（删除 / 外发 / 支付 / 密钥读取）MUST 有人类批准路径。
- **4.3 (SHOULD)** 批准可追溯到人。
- **4.4 (MUST)** 若被治理的 agent 运行在带安全策略的模型/框架之上，MUST **摄入其拦截与告警信号**，
  并能在凭据的 `signals[]` 中以元数据呈现。理由：模型层的控制是概率性的、且由模型厂商持有，
  组织层需要确定性的记录；两层互补——**不摄入，等于组织层面看不见它们**。
- **4.5 (SHOULD)** 采集 SHOULD 能在不要求每位开发者手工操作的前提下完成。
  理由：采纳障碍本身就是被实证的痛点（AvePoint 2026：约 40% 组织因采纳障碍延迟部署）；
  "装在每个开发者笔记本上"会让合规率长期停在低位。

### ASAS-5 可观测与审计
- **5.1 (MUST)** 记录：agent、工具、**当时授权来源**、时间。
- **5.2 (MUST)** **MUST NOT 记录参数值**；默认仅参数名；敏感值脱敏。
- **5.3 (MUST)** 日志防篡改（哈希链）。
- **5.4 (SHOULD)** 保留期与时钟来源可声明。

### ASAS-6 凭据与独立验证
- **6.1 (MUST)** 产出 ASAS-A 凭据：机器可读 + 全部证据的哈希清单。
- **6.2 (MUST)** **第三方离线、零安装可验证**；验证 MUST NOT 依赖签发方在线。
- **6.3 (MUST)** 凭据 MUST 声明未覆盖部分（未知 / 未管 / 只读治理），**不得使读者高估覆盖范围**。
- **6.4 (SHOULD)** 可选签名；**签名 MUST NOT 成为验证前提**。
- **6.5 (MUST)** 变更（新组件、新版本、描述变化、委派变化）MUST 触发重证；过期凭据视为无效。
- **6.6 (MUST)** **可验证的沉默**：事件流 MUST 带单调序号与前序哈希；被评估方 MUST 在本地留存只增摘要；验证方 MUST 能检测序号断裂，并将断裂本身视为事件。

### ASAS-7 合规映射
- **7.1 (MUST)** 映射至 EU AI Act（Art.11/15/17）、ISO/IEC 42001、SOC 2、NIST AI RMF。
- **7.2 (MUST)** 仅声明"**可支撑**哪条要求"；**MUST NOT 声称合规**。

### ASAS-8 事件就绪与遏制
- **8.1 (MUST)** 能在**声明的时间窗内**吊销某 agent 的全部权限（写明分钟数）。
- **8.2 (MUST)** 有隔离手段（kill switch / 凭据回收）。
- **8.3 (MUST)** 能回答"**哪些 agent 曾能触达 X**"。
- **8.4 (SHOULD)** 定期遏制演练并留痕。

## 5. 凭据格式

规范文本：`spec/ASAS-A-v0.1.schema.json`（JSON Schema 2020-12）。

两条设计说明，都直接影响可验证性：

1. **所有对象都是闭集合（`additionalProperties: false`）**。这不是洁癖——**"永不记录参数值"和"未知必须声明"是由 schema 强制执行的，而不是靠承诺**。
2. **`unknown` 是必填字段**（可为空数组）。省略它与"没有未知"是两件不同的事，前者不合规。

## 6. 验证程序 ASAS-V（离线可执行）

验证方 MUST 能在**无网络、不联系签发方**的条件下完成下列全部检查。

| 规则 | 内容 | 不通过 |
|---|---|---|
| **V1 `hashMatch`** | manifest 中每个文件重算 sha256 一致 | 凭据作废 |
| **V2 `narrowingOnly`** | 所有委派满足子集 ⊆ 父集且未过期 | 不合规 |
| **V3 `noUndeclaredUnknown`** | 枚举失败项 MUST 在 `unknown[]` 中声明 | 不合规（审计欺诈） |
| **V4 `everyVerdictHasBasis`** | 每条 allow/approve/deny 都有非空 basis | 不合规 |
| **V5 `allPinnedOrExempt`** | 每个 asset 已定版，或有未过期豁免 | 不合规 |
| **V6 `silenceIsAuditable`** | 事件序号连续、前序哈希相符、与本地摘要一致 | 不合规 |
| **V7 `withinValidityWindow`** | 凭据仍在有效期内（`subject.period.to`） | 凭据失效，必须重证（ASAS-6.5） |

**变更即失效**：`asas-diff` 报出 critical / high 时，凭据视为失效——无论有效期是否到。
这条把 ASAS-6.5 从"一条要求"变成"一条可自动执行的规则"。

### 0.1 草案的一处自我修正（写参考实现时发现）

**问题**：初稿的 schema 要求每个 asset **必须**有 `contentHash`、`version` 是字符串、
`pinned` 是布尔——这等于**逼产出方编造事实**：本机扫描本来就拿不到制品哈希，
拿不到定版状态。一份"必须填"的 schema，会生产出一批看起来很干净、实际是假值的凭据。

**修正**：把四个字段放宽为 `值 | null`，并规定 **null = 未确定，必须出现在 `unknown[]` 里**。
现在形成一条通用规则（可复用于后续版本）：

> **未知可表达三元组**：任何"事实"字段都允许 `null`；允许 `null` 就意味着
> 同时必须在 `unknown[]` 里声明它。**不能表达的未知，一定会变成假值。**

这不是规范变松了，而是变严了：初稿能用假值蒙过去，现在蒙不过去——验证器的 V3
会直接判不合规。
