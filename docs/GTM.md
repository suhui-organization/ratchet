# 分发与推广计划（Marketing-first）

> 目标：**最短时间内拿到最高曝光与最高利润**。
> 前提：没有 OPC 人脉、没有现成受众、没有预算买量。
> 所以只依赖两样：**能被发现的入口** + **自带传播力的内容**。

---

## 0. 一条判断：别把力气花在社交上

社交平台奖励的是**已有受众**。0 粉丝发帖 ≈ 0 曝光——上一代产品实测：3 粉丝、置顶帖 15 浏览。

真正带量的入口是**开发者主动去找工具的地方**：

| 入口 | 为什么比社交强 |
|---|---|
| **官方 MCP Registry** | 开发者在那里**找 server 装**；发布一次级联到 Smithery、PulseMCP、GitHub MCP Registry——一处发布、四处可见 |
| Homebrew | 装 Go 工具的第一直觉就是 `brew install` |
| Docker (GHCR) | 不想装东西的人直接跑容器 |
| awesome-* 清单 | 长期被搜索命中 |

**社交的角色是承接搜索，不是创造曝光。**

---

## 1. 最大缺口：ratchet 进不了 MCP Registry

官方 Registry 收的是 **MCP server**，ratchet 是 CLI。这不是补材料能绕过的。

### 补法：把 ratchet 变成一个 MCP server

让 agent **自己**能问"我到底能碰什么"：

```
ratchet_scan     → 这台机器的 MCP server 清单 + 未锁版本数
ratchet_policy   → 当前策略的三态摘要
ratchet_check    → 给一次假设调用，返回判定（复用 CheckArgs）
```

双向价值：**分发**上能进官方 Registry 并级联四个目录；**产品**上用户可以直接问自己的
agent"我现在的权限面有多大"，不必记命令。

工程量小：判定器已是纯函数，包一层 stdio MCP 即可；Registry 只要求存在公开可取用的制品
（我们已有 GitHub Release / 可加 GHCR）。

> 整份计划里 ROI 最高的一件。**建议第一个做。**

## 2. 渠道清单

### A. 官方与目录（最高优先）

| 渠道 | 动作 | 前提 |
|---|---|---|
| **官方 MCP Registry** | `mcp-publisher publish` | MCP server 形态 + 公开制品 |
| Smithery / PulseMCP / GitHub Registry | 随官方 Registry 自动收录 | 同上 |
| Glama | 提交 `glama.json` + 仓库 | 同上 |
| awesome-mcp-servers / awesome-ai-security-tools | 提 PR（`iversonwuwei` 名下已有这两个仓库，自己的清单也能加） | 仓库公开 |
| Homebrew | 建 tap，formula 指向 GitHub Release | Release 已有 |
| Docker (GHCR) | CI 加一步 build & push | 一次 workflow 改动 |

### B. 社交（承接，不指望它创造）

| 渠道 | 打法 | 纪律 |
|---|---|---|
| X | 带**具体数字**发；链接放第一条回复 | 不写"安全"，只写数字与机制 |
| Hacker News | `Show HN: <一句事实>`，美东上午发，头两小时守评论 | 第一段就承认做不到什么 |
| Reddit r/mcp | 发发现、不发产品；结尾问**别人的数字** | 被问是不是你做的，直接承认 |
| dev.to | 把"我扫了自己的机器"写成教程，canonical 指向自己站点 | 吃 SEO 长尾 |
| Mastodon (infosec.exchange) | 短结论 + 链接（**不降权**） | 语气比 X 更克制 |
| LinkedIn | 讲合规语言（谁能证明 agent 没越权） | 找甲方与同行 |

> **顺序不可颠倒**：先把 Registry / Homebrew 铺好，再发社交。
> 反过来会出现"点进来装不上"，那是把唯一的曝光浪费掉。

## 3. 获客路径

```text
目录/搜索  →  README 首屏（必须是那条安装命令）
          →  curl | sh 装上（已验证可用）
          →  ratchet scan（10 秒出一个数字：未锁版本数）
          →  ┌─ 继续用 → 挂 hook 采语料 → observe → policy
             └─ 要一份能交出去的报告 → 这才是付费点
```

**转化的关键是 scan 出来的那个数字**，不是功能介绍。

| 缺什么 | 卡住 | 补法 |
|---|---|---|
| 可分享的扫描结果页 | 内容没法被转发 | `ratchet scan --share` 生成静态页 |
| README 首屏 | 首屏是介绍不是命令 | 第一行就是安装命令 |
| 落地页部署 | 现在只在本地 | 部署 `web/.output` |

---

## 4. 反馈收集（现在完全没有）

| 层次 | 做法 | 工程量 |
|---|---|---|
| 被动 | GitHub Issues 模板（Bug / 误报 / 功能） | 小 |
| 主动一 | README 与 `--help` 放一句"遇到误报请贴 `ratchet scan` 输出" | 极小 |
| 主动二 | `ratchet feedback`：把去标识化结果写成 issue 正文供用户复制 | 小 |
| 主动三 | **`policy check` 判 deny 时提示"如果这是误报，用 ratchet feedback 发给我们"** | 小 |

> **不做遥测。** 卖点就是"数据不出机器"，加一行上报就毁了它。
> 反馈必须用户主动发起，我们只把"发什么"准备好。

## 5. 利润从哪来

| 产品 | 价格 | 触发点 |
|---|---|---|
| 自助使用 | $0 | 开源核心 |
| **一次性权限审计交付** | **$1,500–8,000** | 客户被问"agent 能碰什么"，答不上来 |
| 证据托管（可选） | $X/月/客户 | 交付物需长期可访问 |

**不做 $9–19 订阅**：同类开源已把这一档压到零，且无数据支持个人付费。

利润率杠杆在**交付自动化**：一次交付现在要 30–60 分钟人工；把
`scan → observe → policy → 报告 → 分享` 串成一条命令，同样时间能交付 5 份。

## 7. 90 天节奏

| 周 | 做什么 | 判据 |
|---|---|---|
| 1 | G1 + G6 + G7 | 官方 Registry 能搜到；README 首屏是安装命令 |
| 2 | G2 + G3 + G4 | `brew install` 可用；结果页能分享 |
| 3 | 发第一篇（"我扫了自己的机器：12/16 未锁版本"），同步 HN / r/mcp / dev.to | 首周 ≥30 star |
| 4–6 | G5 + 按反馈修误报；每周 1 篇 | 有人提 Issue |
| 7–9 | G8 + 主动找 10 个可能付费的人 | ≥3 次真实交付 |
| 10–12 | 复盘谁付费了、为什么 | ≥1 个付费，或明确的"不买"理由 |

### 什么时候该转向

| 信号 | 含义 | 动作 |
|---|---|---|
| Registry 上了但安装量为 0 | 定位问题，不是分发问题 | 改卖"权限收敛"，别卖证据 |
| 有人装、没人挂 hook | 采集这一环门槛太高 | 做一键装 hook |
| 有人用、没人问价 | 需求真、付费意愿弱 | 转服务化交付 |
| 60 天 0 付费 | 买家不存在 | 拆成开源组件，停止商业化 |
